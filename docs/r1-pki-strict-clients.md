# 内部 TLS 与严格客户端兼容

2026-10-11，本地验收通过；现有部署证书未替换。证据见 [源码与验收摘要](evidence/production-pki-2026-10-11.json)。

旧内部 CA 缺少 `keyUsage` 时，原发布预检能够通过，但 Python 3.13 的默认严格 TLS 客户端拒绝该证书链，错误码为 92。现在 PostgreSQL Secret 生成器显式生成 CA 的关键 `basicConstraints` / `keyUsage`、SKI/AKI，并为服务端证书生成 `serverAuth`、SAN 及独立叶证书约束。生成器仍拒绝覆盖已有 Secret，PostgreSQL 私钥保持 UID 999、0400。

控制面发布预检对内部 HTTPS 使用明确的信任根、完整中间证书链、主机名、服务端用途、严格 X.509 与安全等级 2 校验。中间证书作为不受信输入，不会自动成为信任根。公共浏览器证书仍需单独通过浏览器信任验收。

固定 Python 3.13.5 / OpenSSL 3.5.6 环境中，8 项实际 TLS 回归和完整发布预检通过，覆盖旧缺失 KU、错误用途/主机名/信任根、弱密钥、中间证书及生产生成器的权限与不可覆盖行为。该证据不代表运行中控制面、PostgreSQL 或外部浏览器已经认证。

已有内部证书应由部署负责人按这些约束明确重签、安装，再运行发布预检和真实客户端连接验收；不能仅修改脚本后继续使用旧链。无需重建核心二进制镜像。
